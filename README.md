SUB-UI
======

一个基于 SUB 核心能力构建的公开订阅聚合转换前端。

SUB-UI
保留订阅获取、聚合、去重、NOADS、SUBAPI、SUBCONFIG、格式识别、WARP、主页伪装、管理员登录、二维码、API/CONFIG
管理等核心能力，并提供独立的 Web 管理界面。

功能
==

公开页面
====

•   订阅链接聚合
•   多个订阅地址合并
•   自建节点与订阅地址混合聚合
•   节点去重
•   NOADS 节点屏蔽
•   SUBAPI 订阅转换后端
•   SUBCONFIG 订阅转换规则
•   自动识别订阅格式
•   Clash / Mihomo
•   Sing-box
•   Surge
•   Quantumult X
•   Loon
•   Base64 等订阅格式
•   聚合订阅链接生成
•   二维码
•   一键复制
•   聚合订阅链接销毁
•   可选销毁密钥
•   浏览器本地保存已生成链接

管理后台
====

管理员路径默认为：

/admin

管理员路径可以在「站点」设置中修改。

管理后台支持：

•   SUB 聚合节点管理
•   SUB 长按拖动排序
•   SUB 添加、编辑、删除
•   URL 管理
•   SUBAPI 管理
•   SUBCONFIG 管理
•   默认 SUBAPI 设置
•   默认 SUBCONFIG 设置
•   NOADS 配置
•   管理员账号密码设置
•   管理员路径设置
•   站点名称设置
•   全站 Logo 设置
•   聚合订阅链接数量统计
•   聚合订阅 JSON 管理

聚合订阅 JSON 管理
============

访问：

/管理员路径/json

例如管理员路径是：

apple

则 JSON 管理页面：

/apple/json

JSON 管理页面支持：

•   搜索 JSON 内容
•   搜索 Token
•   查看单个 JSON
•   单个删除
•   勾选多个 JSON 后批量删除
•   全部删除
•   刷新
•   返回管理员后台

删除 `URL:<token>` 对应 JSON 后，该聚合订阅链接会立即失效。

> 搜索只是筛选结果，不会自动删除搜索结果。需要删除时，可以单独删除，也可以勾选需要删除的项目后批量删除。

------------------------------------------------------------------------

数据存储
====

SUB-UI 只需要一个 Cloudflare KV Namespace。

KV Binding 名称必须设置为：

KV

主要数据：

CONFIG.json
SUB:<id>
URL:<token>

CONFIG.json
===========

用于保存站点和管理员相关配置，包括：

•   管理员账号
•   管理员密码
•   管理员路径
•   站点名称
•   Logo
•   其他站点配置

SUB:`<id>`{=html}
=================

用于保存聚合节点配置。

URL:`<token>`{=html}
====================

用于保存已经生成的公开聚合订阅 JSON。

每次生成聚合订阅都会生成新的随机 Token，不复用已有 Token。

------------------------------------------------------------------------

部署
==

SUB-UI 支持两种部署方式：

1.  Cloudflare Workers
2.  Cloudflare Pages

两种方式都需要绑定 Cloudflare KV。

------------------------------------------------------------------------

一、Cloudflare Workers 部署
=======================

1. 创建 KV
========

进入 Cloudflare：

Workers & Pages
→ KV
→ Create a namespace

创建一个 KV Namespace。

名称可以自定义，例如：

SUB-UI

名称本身不影响程序。

------------------------------------------------------------------------

2. 创建 Worker
============

进入：

Workers & Pages
→ Create
→ Workers

创建一个新的 Worker。

将项目中的：

_worker.js

完整代码部署到 Worker。

------------------------------------------------------------------------

3. 绑定 KV
========

进入 Worker：

Settings
→ Bindings
→ KV Namespace

添加 KV Namespace。

变量名称必须是：

KV

然后选择刚刚创建的 KV Namespace。

最终应该是：

KV → 你的 KV Namespace

不要使用：

SUB

或者其他变量名。

程序固定读取：

env.KV

------------------------------------------------------------------------

4. 设置环境变量
=========

在 Worker：

Settings
→ Variables and Secrets

根据需要添加环境变量。

USER
====

管理员账号。

例如：

admin

PASS
====

管理员密码。

例如：

your-password

如果设置了 USER 和 PASS，管理员页面会启用登录保护。

URL
===

旧版主页伪装 URL。

可选。

URL302
======

旧版 302 跳转地址。

可选。

CODE
====

主页伪装相关配置。

可选。

SUBUPTIME
=========

订阅更新时间配置。

可选。

WARP
====

WARP 节点配置。

可选。

LINK
====

旧版节点链接配置。

可选。

LINKSUB
=======

旧版订阅链接配置。

可选。

> 管理员路径不再通过 TOKEN 环境变量控制。首次启动默认使用
> `/admin`，之后可以直接在管理员后台「站点」中修改。

------------------------------------------------------------------------

5. 部署
=====

保存并部署 Worker。

部署完成后访问：

https://你的域名/admin

如果没有设置 USER / PASS，则不会启用管理员登录验证。

------------------------------------------------------------------------

二、Cloudflare Pages 部署
=====================

1. 创建 KV
========

和 Workers 部署一样，先创建 Cloudflare KV Namespace。

然后记住：

KV Namespace

------------------------------------------------------------------------

2. 准备 Pages 项目
==============

创建 Cloudflare Pages 项目。

本项目使用 Pages Functions 的 Worker 模式。

项目结构：

项目根目录/
└── functions/
    └── _worker.js

将本项目完整的：

_worker.js

放到：

functions/_worker.js

不要只复制其中一部分代码。

------------------------------------------------------------------------

3. 绑定 KV
========

进入 Pages 项目：

Settings
→ Functions
→ KV Namespace Bindings

添加 KV Namespace。

变量名称必须填写：

KV

然后选择之前创建的 KV Namespace。

最终：

KV → 你的 KV Namespace

------------------------------------------------------------------------

4. 设置环境变量
=========

进入：

Settings
→ Environment variables

根据需要添加：

USER
PASS
URL
URL302
CODE
SUBUPTIME
WARP
LINK
LINKSUB

其中最重要的是：

USER
PASS

它们用于管理员登录。

管理员路径默认：

/admin

之后可以在后台修改。

------------------------------------------------------------------------

5. 部署
=====

提交项目并触发 Pages 部署。

如果是在已经部署完成后新增：

KV
USER
PASS

等变量或 Binding，需要重新部署，使新的配置正式生效。

------------------------------------------------------------------------

管理员登录
=====

默认管理员地址：

/admin

如果管理员路径修改为：

apple

则：

/apple

JSON 管理页面：

/apple/json

退出：

/apple/logout

管理员路径只能使用：

•   字母
•   数字
•   `_`
•   `-`

长度：

2-60

------------------------------------------------------------------------

聚合订阅生成
======

公开页面填写：

订阅链接
SUBAPI
SUBCONFIG
NOADS
密钥（可选）

点击：

生成聚合订阅链接

系统会生成一个新的随机 Token。

例如：

https://example.com/AbCdEf12

每次生成都会创建新的：

URL:AbCdEf12

JSON。

不会因为内容相同而复用旧链接。

------------------------------------------------------------------------

聚合订阅销毁
======

生成聚合订阅时可以填写：

密钥

密钥用于保护公开页面上的：

销毁本链接

如果生成时设置了密钥：

销毁
→ 输入密钥
→ 验证
→ 删除 URL:<token>

如果没有设置密钥：

销毁
→ 确认
→ 删除 URL:<token>

删除之后：

https://example.com/AbCdEf12

将不再有效。

------------------------------------------------------------------------

JSON 管理
=======

管理员进入：

/管理员路径/json

页面会读取 KV 中：

URL:

开头的项目。

例如：

URL:AbCdEf12
URL:XyZ12345
URL:Klm78901

搜索
==

输入关键字后进行搜索。

搜索的是 JSON 内容，因此可以搜索：

•   Token
•   订阅地址
•   SUB
•   URL
•   SUBAPI
•   SUBCONFIG
•   NOADS
•   JSON 中其他字段

搜索不会删除任何数据。

单个删除
====

搜索结果中的每个 JSON 都可以单独：

查看 JSON
删除

删除后对应的公开订阅 URL 立即失效。

批量删除
====

可以勾选需要删除的项目：

☑ JSON A
☑ JSON C
☑ JSON F

然后：

删除选中

只删除选中的项目。

全部删除
====

使用：

全部删除

会删除当前所有聚合订阅 JSON。

此操作会使现有聚合订阅链接全部失效。

------------------------------------------------------------------------

安全建议
====

建议正式使用时设置：

USER
PASS

并修改默认管理员路径：

/admin

例如：

/apple

管理员路径修改后，旧管理员路径不会作为新的管理入口使用。

同时建议：

•   不要公开 USER / PASS
•   不要公开 KV Namespace
•   不要把包含敏感信息的环境变量提交到 GitHub
•   不要把管理员路径设置成过于明显的名称
•   删除 JSON 前确认对应订阅链接是否仍在使用

项目结构
====

SUB-UI 当前项目采用**根目录直接放置 Worker 文件**的结构，不使用 `functions/_worker.js`。

项目结构：

SUB-UI/
├── .github/
│   └── workflows/
│       └── sync.yml
├── _worker.js
├── wrangler.toml
└── README.md

其中：

• `_worker.js`：SUB-UI 主程序
• `wrangler.toml`：Cloudflare Wrangler 配置
• `.github/workflows/sync.yml`：GitHub Actions 工作流
• `README.md`：项目说明文档

Workers 部署
==========

Workers 直接使用项目根目录的：

_worker.js

不需要移动到其他目录。

Pages 部署
========

Pages 部署同样使用项目根目录的：

_worker.js

**不要创建：**

functions/_worker.js

也不要把 `_worker.js` 移动到 `functions` 目录。

Cloudflare Pages 的具体构建设置以项目当前的 Pages 配置为准。

注意事项
====

1. KV Binding 名称必须是 KV
======================

正确：

KV

错误示例：

SUBKV
KV_NAMESPACE
SUB_UI

2. 不要修改 KV Key 前缀
=================

程序使用：

CONFIG.json
SUB:
URL:

不要随意修改。

3. 不要重复部署不同版本
=============

如果之前部署过旧版本，建议先确认当前 Worker / Pages 项目实际使用的
`_worker.js` 是本版本。

4. 修改环境变量后重新部署
==============

尤其是 Pages，在修改环境变量或 KV Binding 后应重新触发一次部署。
